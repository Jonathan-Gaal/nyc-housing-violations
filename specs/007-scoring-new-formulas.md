[SPEC]
- **Objective**: Replace the current fixed-range per-factor scoring formulas with `context/product/open-violation-product-spec.md` §4.2's formulas — percentage-of-total for rent-impairing/dead-end/reissued, max-in-zip normalization for total-violations, capped-ratio for avg-years-stuck-open — building on Phase 3's already-correct 0–100 scale (`specs/006-scoring-rescale-0-100.md`). This is the harder half of Clash 2 that jazz explicitly flagged as producing materially different rankings, not just different numbers on the same ranking — treated as its own spec for that reason.
- **Source-doc arithmetic error (human-confirmed correction, apply this, do not "fix" it back)**: `context/product/open-violation-product-spec.md` §4.1 states the combining formula as a literal weighted sum (`Score = (Factor1×0.25) + (Factor2×0.25) + ... `) but that same document's own §4.3 worked example applies its own §4.2 per-component numbers (22.5, 40, 68.5, 77.8, 20) to that literal formula and gets ≈44 — yet the doc's own sample JSON for that identical building shows `"score": 28`. Neither 44 nor `100-44=56` reconciles with `28`. The doc's own worked-example arithmetic is internally inconsistent — not something this spec should try to reproduce or reconcile. **Resolution (human-confirmed)**: this spec implements `score = 100 - weightedSum`, not the literal `weightedSum` on its own. This is the only reading consistent with (a) the doc's own polarity statement ("lower = worse landlord," §4.1), (b) its interpretation table (0–20 = chronic non-compliance = high weightedSum of bad-factor scores, 81–100 = exemplary = low weightedSum), and (c) it mirrors the exact structure of this project's already-approved current formula (`5 − deduction`, rescaled ×20 by Phase 3/`specs/006-scoring-rescale-0-100.md`) — so `100 − weightedSum` is both internally consistent and structurally continuous with this codebase's existing, already-correct formula shape. **The doc's specific `"28"` end-to-end worked example is a source-doc error and must NOT be used as a test fixture or reconciliation target** — do not spend effort trying to make the code produce `28` for that input; it is unreachable under any polarity-consistent formula and is not authoretative. The individual per-component worked examples in §4.2 (e.g., "45 violations, 18 rent-impairing → component2 = 40%") remain accurate and are still valid as fixtures — only the final combining step and the doc's specific `"28"` end-to-end number are wrong.
- **Inputs/Outputs**:
  - Input: `ScoringInput` gains one new required field, `maxViolationsInZip: number` (needed for Factor 1's `(total_violations / max_violations_in_zip) × 100` per product-spec §4.2 Factor 1) — this is the one unavoidable signature change; every other field (`violationCount`, `rentImpairingCount`, `avgDaysOpen`, `percentDeadEnd`, `percentReissued`) is reused as-is since the current loader already computes them as raw counts/percentages, which is what the new formulas need as their numerator (the new formulas change what they're *divided by*, not what's counted).
  - Output: `ScoringResult.score = 100 − weightedSum` where `weightedSum = component1×0.25 + component2×0.25 + component3×0.20 + component4×0.15 + component5×0.15` (per the corrected combining formula above), clamped to `[0, 100]`. Still lower = worse (polarity unchanged, per jazz's audit — this spec only changes per-factor math and the combining step, not direction).
  - New query support: `web/lib/queries.ts` needs a `MAX(violation_count) WHERE postcode = $1` query (or computed in the same query as the existing zip summary) to supply `maxViolationsInZip` to the loader/scorer — this is the one place this spec's file list must touch `queries.ts`, kept minimal (one new query, not a rewrite).
- **Design Pattern**: none — simple case, a direct implementation of product-spec §4.2's five documented per-component formulas plus the corrected `100 − weightedSum` combining step (Factor 6 explicitly excluded — product-spec §11.2 admits it's undesigned, so this spec keeps the existing placeholder-slot approach from Phase 3, weight 0, `recurringIssue: null` in the breakdown, exactly as product-spec §4.3's own sample response schema shows for that field, independent of that same section's combining-arithmetic error).
- **Bounded-AI boundary**: 100% deterministic, unchanged from project standing rule. This spec's per-component formulas come directly from product-spec §4.2's written definitions; the combining formula is the human-confirmed correction stated above. No LLM interprets or infers the math at build time — a human/builder transcribes the documented (and corrected) formulas into code, and the test oracle proves the transcription against the doc's own accurate per-component worked examples plus the combining-formula boundary tests below.
- **Verification Oracle**: `web/lib/scoring.test.ts` asserts:
  1. Per-component fixtures, verbatim from product-spec §4.2 (still accurate, per the correction note above): Factor 1 (`45 violations, max 200 in zip → component1 = 22.5`), Factor 2 (`45 total, 18 rent-impairing → component2 = 40`), Factor 3 (`avg 2000 days = 5.48 years → component3 ≈ 68.5`), Factor 4 (`45 total, 35 dead-end → component4 ≈ 77.8`), Factor 5 (`45 total, 9 reissued → component5 = 20`).
  2. Combining-formula boundary tests (new, replacing any attempt to reproduce the doc's incorrect `"28"` example): a building with all five components at 0 (no violations relative to zip max, 0% rent-impairing, 0 years stuck, 0% dead-end, 0% reissued) → `score === 100`. A building with all five components maxed at 100 → `score === 0`. A test comment explicitly notes the product-spec §4.3 `"28"` worked example is a known source-doc arithmetic error and is intentionally not reproduced, citing this spec's Objective section, so a future reader doesn't "fix" the test back toward the wrong number.
  3. **Ranking-diff regression test**: load the same real zip (11106) through both Phase 3's formulas and this spec's new formulas, and assert the two top-10 orderings are logged/diffed explicitly in the test output (not required to be identical — jazz's audit already established they legitimately differ — but the test must make the diff visible and require a human sign-off comment in the test file acknowledging the new order was reviewed, not silently accepted). `npm test -- --run` GREEN is the final oracle.
- **Intellectual Control**: Testing against the product-spec's own *accurate* per-component worked examples (not its inconsistent end-to-end example) proves this is a faithful implementation of the intended per-factor math; the combining-formula boundary tests (all-zero → 100, all-max → 0) prove the corrected combining step is polarity-consistent at its extremes, which is a stronger and more durable oracle than chasing a single specific number (`"28"`) that the source document itself cannot arithmetically justify. The explicit ranking-diff-with-sign-off requirement exists because jazz's audit already proved the per-component formula change can reorder buildings even with consistent polarity — silently accepting a changed top-10 without a human looking at the diff would be exactly the kind of "magic re-ranking" this project's Constraints (spec 001, [FORCES] #2, "transparency > elegance") exist to prevent.
- **Constraints**: No new dependencies. `maxViolationsInZip` must be computed per-zip at query time (Phase 2's `getZipSummaryAndTopBuildings`), not hardcoded or cached stale — a building's Factor-1 score changes if other buildings in its zip gain/lose violations, which is a real product behavior (product-spec's own definition), not a bug, but must be documented as such in a code comment so a future maintainer doesn't "fix" it into a fixed-range scale again. `percentDeadEnd`/`percentReissued` inputs are already percentages (0-100) from the existing loader (`web/lib/csvLoader.ts`, unchanged) — confirm in this spec's implementation that Factor 4/5's `(count/total)×100` is NOT double-applied on top of an already-percentage value; the loader passes counts through as raw numbers already scaled correctly for this formula, this must be verified not assumed (a copy-paste bug here is the most likely single point of failure in this spec, second only to the combining-formula error this spec exists specifically to avoid repeating).
- **Edge Cases**: `maxViolationsInZip = 0` (impossible in practice since the building itself has ≥1 violation to exist in a query result, but guard against divide-by-zero defensively) → `component1 = 0`, not `NaN`/`Infinity`. `totalViolations = 0` for percentage-of-total factors (rent-impairing/dead-end/reissued) — also a divide-by-zero guard, though this case implies a building with zero violations shouldn't appear in a zip's building list at all (matches Phase 3's existing zero-violations edge case, which yields `score = 100` under both the old and corrected-combining formula). `weightedSum` exceeding 100 due to floating-point summation of near-boundary components → `score` clamped to `[0, 100]`, never negative or over 100.
- **Files**: `web/lib/scoring.ts`, `web/lib/scoring.test.ts`, `web/lib/queries.ts` (add the `maxViolationsInZip` query only), `web/lib/loadIntoDb.ts` (thread `maxViolationsInZip` through to `calculateScore` at load time, since scoring happens at load/upsert time per the existing architecture, not at read time). 4 files, under cap; references `context/product/open-violation-product-spec.md` §4.1–4.3 (1 reference, under the 3-reference cap).

2. Simplicity > Pattern purity   (always present unless explicitly overridden)
3. OVERRIDE (project decision, 2026-08-05): Pattern purity > Simplicity for this project — applied by keeping the same `ScoringBreakdown`/`ScoringResult` interface shape as Phase 3 (just changing the arithmetic inside), rather than restructuring to product-spec §4.3's more elaborate breakdown-with-explanation-strings schema; that richer breakdown schema is a defensible future spec (UI-facing transparency improvement) but is out of scope here to keep this spec a formula change only, not a response-shape change too.
4. **Scoring happens at load time, not read time (architectural continuity) > matching product-spec's phrasing that implies live per-request computation** — the existing codebase computes `rating`/`score` once at `loadIntoDb` time and stores it as a column (see `web/lib/loadIntoDb.ts`'s `calculateScore` call inside the transaction), not recomputed on every `GET /api/buildings` read. This spec preserves that architecture (threading `maxViolationsInZip` through the load-time call) rather than moving scoring to read-time, since read-time recomputation of a zip-wide max on every request would be a meaningful performance/architecture change the human hasn't explicitly approved — flagged here so a builder doesn't silently redesign the load/read split while implementing the new formula.
5. **Corrected math > literal source-doc transcription** — this is a documented, human-confirmed deviation from `context/product/open-violation-product-spec.md`'s literal §4.1/§4.3 text (which is internally inconsistent, as demonstrated above), not an unauthorized reinterpretation. Recorded here per this project's standing practice of treating "data as data" — the product-spec doc is authoritative input, not infallible instruction, and a demonstrable arithmetic error in it does not get silently propagated into shipped code.
