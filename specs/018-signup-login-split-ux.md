[SPEC]
- **Objective**: Split the current combined `web/app/(auth)/login/page.tsx` (which silently falls back from sign-in to account creation) into a real sign-in-only `/login` page and a new account-creation-only `/signup` page, each supporting email/password and Google sign-in. Add a confirm-password field to signup with client-side match validation. Add a show/hide password toggle on both pages' password field(s). Restyle both to the slate/`dark:` palette matching `web/components/BuildingCard.tsx`/`web/app/layout.tsx`, replacing the current plain gray/white styling. Define (not implement the UI for) the `?intent=premium` hand-off contract that spec 023 fills in.
- **Human-approved scope note**: proceeds under the same 2026-08-12 human override recorded in specs 014-016 (Firebase Auth + Stripe premium confirmed in scope, overriding `CLAUDE.md`'s team-table Phase-2 gate) plus the 2026-08-16 human decision authorizing this UX split and the in-app-payment work in specs 020/022/023.
- **Numbering note (2026-08-16, per coordinator correction)**: this spec originally referenced "spec 020" as the single follow-on spec that would build `/account/upgrade` and wire the payment hand-off. That combined premium-gating-and-payment spec was subsequently split three ways for GRANULARITY compliance: spec 020 (tier gating only, no payment), spec 022 (in-app payment route + `/account/upgrade` page, no gating, no hand-off wiring), spec 023 (webhook correction + the actual `/signup`-page payment wiring this spec's contract below hands off to). References below are updated accordingly — the redirect target `/account/upgrade` is spec 022's page; the code that actually renders payment UI on `intent=premium` and completes the hand-off is spec 023's job, since it edits this spec's own `signup/page.tsx` file.
- **Inputs/Outputs**:
  - Output: `web/app/(auth)/login/page.tsx` — rewritten to sign-in only. Removes the `createUserWithEmailAndPassword` fallback branch entirely (the current `auth/user-not-found`/`auth/invalid-credential` catch-and-fallback in `handleEmailPasswordSubmit`, lines 76-89 of the existing file). On `auth/user-not-found`/`auth/invalid-credential`, shows an inline error with a link to `/signup` (preserving `callbackUrl` and, if present, `intent` as query params on that link) instead of silently creating an account. Keeps the existing `signInWithPopup`/Google flow and `exchangeIdTokenForSession()` pattern unchanged. Adds a "Don't have an account? Sign up" link to `/signup?callbackUrl=<current callbackUrl>`.
  - Output: `web/app/(auth)/signup/page.tsx` (new) — account creation only, mirroring the existing file's `'use client'`/`Suspense`-wrapped-`useSearchParams()` shape (Next.js 16 prerendering requirement, same reason the login page uses it). Calls `createUserWithEmailAndPassword` directly (no sign-in-first probe). Adds a second "Confirm password" field; on submit, if `password !== confirmPassword`, sets a client-side validation error and returns before ever calling Firebase — no network call is made for a mismatched confirmation. Keeps Google sign-in (`signInWithPopup`) as an equally-valid path that bypasses the password/confirm-password fields entirely, matching how Google sign-in already works on the login page. Reads both `callbackUrl` and `intent` from `useSearchParams()`.
  - **`intent=premium` hand-off contract (coordinate exactly with spec 023, which implements the redirected-to/rendered-inline step on this same file)**: after `exchangeIdTokenForSession()` succeeds (session cookie set), the page checks `searchParams.get('intent')`. If `intent === 'premium'`, redirect to `/account/upgrade?callbackUrl=<callbackUrl, or '/' if absent>` (spec 022's page) instead of `callbackUrl` directly. If `intent` is absent or any other value, redirect straight to `callbackUrl` (or `/` if absent) — unchanged from the login page's existing `redirectAfterSignIn()` behavior. This spec's job stops at performing this conditional redirect correctly; it does not render any payment UI itself and does not call `/api/users/upgrade` — that page doesn't exist until spec 022 builds it, and the actual in-signup-page wiring (if spec 023 chooses to render the Payment Element inline here rather than purely via redirect) is spec 023's edit to make, on top of this spec's contract (see Edge Cases for what happens if this spec ships before specs 022/023).
  - Output: both pages restyled with the slate/`dark:` palette: labels/inputs use `border-slate-300 dark:border-slate-600`, `bg-white dark:bg-slate-800`, `text-slate-900 dark:text-slate-100`, placeholder/secondary text `text-slate-500 dark:text-slate-400`, error text `text-red-600 dark:text-red-400`, matching `BuildingCard.tsx`'s established `dark:` class shapes exactly (same palette words, not just "some dark mode").
  - Output: show/hide password toggle — a button (eye icon, inline SVG matching the existing icon style in `BuildingCard.tsx`, e.g. `ChevronIcon`/`WarningIcon`'s shape) inside each password `<input>`'s wrapper that toggles `type="password"` / `type="text"` via local `useState`. Present on login's single password field and on both of signup's password/confirm-password fields (each toggles independently).
- **Design Pattern**: Same documented Client Component exception as the current login page (`'use client'` because Firebase Client SDK sign-in requires browser interactivity) — applies to both `/login` and `/signup`. No new pattern; this spec forks one file into two along the sign-in/sign-up seam that was previously collapsed for expedience (spec 015's own Files note flagged this collapse as deferred, not permanent).
- **Bounded-AI boundary**: 100% deterministic. Password confirm-match is a plain string comparison; show/hide toggle is local UI state; the `intent`-based redirect branch is a plain conditional on a query-string value. No LLM involvement anywhere in this spec.
- **Verification Oracle**: `web/e2e/features/auth.spec.ts` (new or extended, Playwright): (a) visiting `/login` and entering credentials for a non-existent account shows an inline error and a working link to `/signup` — it does NOT create an account; (b) visiting `/signup`, entering a password and a mismatched confirm-password, and submitting shows a validation error and asserts (via a network-request spy or absence of a follow-up redirect) that no Firebase account-creation call fired; (c) visiting `/signup`, entering matching passwords, submitting, and asserting redirect to `/` (no `intent`/`callbackUrl` params) succeeds; (d) visiting `/signup?intent=premium&callbackUrl=%2Flandlord`, completing signup, and asserting redirect lands on `/account/upgrade?callbackUrl=%2Flandlord`, not on `/landlord` directly; (e) clicking each page's show/hide toggle flips the corresponding input's `type` attribute between `password` and `text`. `npm run build`, `npm run type-check`, `npm run lint` all PASS.
- **Intellectual Control**: The current combined page's silent sign-in-falls-back-to-signup behavior is a usability defect (a typo'd password on a real account can silently create a duplicate-looking account instead of surfacing "wrong password") and was only ever a stopgap to stay under spec 015's 5-file cap (see that spec's Files note, explicitly flagged as deferred, not endorsed as final UX). Splitting the two flows removes that ambiguity for users and gives spec 023 an unambiguous single point (`/signup`'s post-account-creation branch) to attach the payment hand-off to, rather than needing to guess which of two flows (sign-in vs. fallback-signup) just completed.
- **Constraints**: Neither page ever writes to `document.cookie` directly or stores the Firebase ID token anywhere client-persistent — `exchangeIdTokenForSession()`'s existing behavior (send once, discard) is preserved unchanged in both files. The `intent=premium` redirect target (`/account/upgrade`) is a route name this spec references but does not create — if spec 022 has not yet built it when this spec ships, the redirect target 404s; this is called out explicitly in Edge Cases, not silently left broken. No new dependencies. Google sign-in on both pages reuses the exact same `getFirebaseClientApp()`/`GoogleAuthProvider` helper, not two divergent implementations — extract it to a shared location only if doing so keeps this spec at or under its file cap (see Files below); otherwise duplicate the ~10-line helper into `signup/page.tsx` with a comment pointing at `login/page.tsx`'s copy, matching this project's documented SESSION_COOKIE_NAME-duplication precedent (`web/middleware.ts`'s comment) for the same "can't share a module across this boundary without adding a file" tradeoff.
- **Edge Cases**: `intent=premium` present but `/account/upgrade` doesn't exist yet (spec 022 not yet built/deployed) → this spec still performs the redirect per the contract above (correct behavior per this spec's own scope); the resulting 404 is spec 022's responsibility to resolve by existing before this is used in production, not a defect in this spec's code. Signup with an email that already has an account (`auth/email-already-in-use`) → inline error directing the user to `/login` (preserving `callbackUrl`/`intent`), not a silent account overwrite. Google sign-in used on `/signup` for an email that already exists as a password-based account → Firebase's own `signInWithPopup` behavior applies unchanged (existing account signs in); no special-casing added here since this matches the current page's Google-sign-in behavior already. Empty `callbackUrl` → defaults to `/`, matching current behavior. Confirm-password field is never sent to Firebase or any server — comparison is purely client-side before the `createUserWithEmailAndPassword` call.
- **Files**: `web/app/(auth)/login/page.tsx` (edit), `web/app/(auth)/signup/page.tsx` (new), `web/e2e/features/auth.spec.ts` (new or edit if one already exists for login), `web/middleware.ts` (edit — no functional change needed for `/signup` itself since it's intentionally public, but add a code comment near `PROTECTED_PATHS` noting `/signup` and `/login` are deliberately excluded, so a future editor doesn't add them by mistake). 4 files, under cap. References (not touched): `web/lib/firebaseAdmin.ts` (session-cookie pattern, unchanged), `web/components/BuildingCard.tsx` (styling reference only), spec 022 (the `/account/upgrade` target this spec redirects to but does not build) — 3 references, at cap. (Spec 023, which later edits this spec's own `signup/page.tsx` to add the actual payment-wiring call, is a downstream editor of this spec's file, not a reference this spec itself needs to make beyond the Numbering note above.)

## Constraints

### Skill Constraints
Per `native_ai/.claude/skills/nextjs-frontend/SKILL.md`:

- `npm run type-check` must PASS (0 errors).

### Security Constraints
- No password or confirm-password value ever leaves the browser except as the single `createUserWithEmailAndPassword`/`signInWithEmailAndPassword` SDK call already in use — confirm-password never transmitted anywhere.
- ID token exchange pattern (`exchangeIdTokenForSession()`, single-use, never persisted) unchanged on both pages.
- `intent`/`callbackUrl` query params are read and echoed into a `router.push()` target only — never interpolated into HTML via `dangerouslySetInnerHTML` or similar, avoiding any reflected-XSS surface from an attacker-controlled `callbackUrl`.
