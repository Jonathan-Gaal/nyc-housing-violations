[SPEC]
- **Objective**: Replace `web/app/api/users/upgrade/route.ts`'s Stripe Checkout redirect (spec 016) with an in-app PaymentIntent/subscription flow, and add the client-side Payment Element UI to confirm payment without leaving this app. Returns `{ clientSecret }` instead of `{ checkoutUrl }`. Adds the new client dependencies `@stripe/stripe-js`/`@stripe/react-stripe-js` (authorized here, per this project's DEPENDENCY AUTHORITY rule). **Correcting the webhook event this flow fires** and **wiring spec 018's signup `intent=premium` hand-off to this page** are **spec 023**, which depends on this spec's `/account/upgrade` page existing.
- **Human-approved scope note**: proceeds under the 2026-08-12 override (specs 014-016) plus the 2026-08-16 human decision authorizing the switch to in-app payment.
- **Split note (2026-08-16, per coordinator correction)**: this is the payment-route/payment-page half of what was originally drafted as a single, larger premium-gating-and-payment spec (see spec 020's Split note). Split further from spec 020 (gating) because gating and "how a user pays" are separable, and split from spec 023 (webhook correction + signup wiring) because this spec's own file list (route rewrite + new page + client SDK singleton + dependency addition) already reaches the 5-file cap on its own without also touching the webhook route or spec 018's signup page.
- **Scoped reversal of spec 016 Force #3, stated explicitly, not silently**: spec 016 chose Stripe Checkout redirect over custom Stripe Elements specifically "for PCI-scope minimization" (its Force #3, and its Security Constraints: "No sensitive card data ever touches this app's servers"). This spec reverses that choice, per explicit 2026-08-16 human decision, and adopts Stripe's **Payment Element** (not a raw custom card-number `<input>`) — Payment Element is still a PCI-SAQ-A-eligible, Stripe-hosted-iframe component (card data is entered into a Stripe-controlled iframe, never touching this app's own DOM/JS/servers, exactly as Checkout also guaranteed) — so the PCI-scope property spec 016 cared about is preserved even though the redirect-vs-embedded UX choice is reversed. This is a scoped reversal of one design choice (redirect vs. embed), not a rollback of the security property that motivated it.
- **Inputs/Outputs**:
  - Output (edit): `web/app/api/users/upgrade/route.ts` — after the existing `verifySessionCookie()`/`findUserForUpgrade`/Stripe-customer-reuse-or-create logic (all unchanged), replace the `stripeClient.checkout.sessions.create(...)` call with `stripeClient.subscriptions.create({ customer: stripeCustomerId, items: [{ price_data: {...} }], payment_behavior: 'default_incomplete', expand: ['latest_invoice.payment_intent'], metadata: { firebase_uid } })`, then extract `subscription.latest_invoice.payment_intent.client_secret` and return `{ clientSecret }` (`200`) instead of `{ checkoutUrl }`. The route's own response still never writes `users.tier` — unchanged invariant from spec 016, re-tested here since this spec rewrites the route's success-path body (the piece most at risk of regressing it).
  - Output (edit): `web/app/api/users/upgrade/route.test.ts` (spec 016's existing test file) — extended with a **mocked Stripe SDK** (matching how spec 016 already mocks Stripe for its webhook-signature tests — no real `sk_test_` key required) asserting: a valid-session request calls `stripeClient.subscriptions.create` with `payment_behavior: 'default_incomplete'` and `expand: ['latest_invoice.payment_intent']`, and the route's JSON response is `{ clientSecret: <mocked value> }`, NOT `{ checkoutUrl: ... }`; plus an assertion that no `UPDATE users SET tier` query fires during the test (proving the webhook-as-source-of-truth invariant survived this spec's edit). Spec 016's existing missing-cookie-→-`401` test continues to pass unmodified.
  - Output: `web/app/account/upgrade/page.tsx` (new) — a payment page. Client Component: on mount, `POST /api/users/upgrade` (requires the session cookie already be set), receives `{ clientSecret }`, renders `<Elements stripe={stripePromise} options={{ clientSecret }}><PaymentElement /></Elements>` (from `@stripe/react-stripe-js`) inside a confirm-payment form calling `stripe.confirmPayment({ elements, confirmParams: { return_url: ... } })` on submit — payment is confirmed in-app via Stripe.js, the browser never navigates to a stripe.com-hosted page. On confirmed success, redirects to `?callbackUrl` (or `/` if absent) — this redirect happens on payment-confirmation success, NOT on any assumption about `users.tier`, since the webhook (spec 023's job to correct, unchanged by this spec) is still the only writer of that column; the page shows a brief "processing" state if the webhook hasn't landed yet by the time the user reaches `callbackUrl` (Edge Cases). Accepts a `callbackUrl` query param (this spec's own contract — the value is only ever consumed here for the post-payment redirect, not otherwise validated/parsed beyond being used as a relative path).
  - Output: `web/lib/stripeClient.ts` (new) — client-side singleton, `loadStripe(process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY)` from `@stripe/stripe-js`, mirroring the `getXxx()` singleton-getter naming convention used elsewhere (`getPool`, `getFirebaseAdmin`, `getStripeClient`) — named `getStripeJsPromise()` to disambiguate from the server-side `getStripeClient()` in `web/lib/stripe.ts`.
  - Output (edit): `web/package.json` — add `@stripe/stripe-js` and `@stripe/react-stripe-js` as dependencies, **authorized here per this project's DEPENDENCY AUTHORITY rule**: both are Stripe's own first-party packages, the standard, documented pairing for an embedded Payment Element integration; no alternative library considered, since this is Stripe's canonical client SDK for this exact use case.
- **Design Pattern**: Payment confirmation happens entirely client-side via Stripe.js against a server-issued `clientSecret` — the server never sees card data and never itself confirms payment; this mirrors the existing division of responsibility from Checkout (Stripe hosts the sensitive step), just embedded instead of redirected.
- **Bounded-AI boundary**: 100% deterministic. Payment confirmation is Stripe's own SDK/API; this spec contains no scoring, ranking, or LLM-generated content. `users.tier` is not written by any code in this spec at all (see Constraints) — it remains exclusively the webhook's responsibility, corrected in spec 023.
- **Verification Oracle** (per the human's explicit instruction, provable without live Stripe/DB/Firebase credentials — same "credential-blocked" posture as spec 016, see `.env.example`'s existing note on that spec):
  - `web/app/api/users/upgrade/route.test.ts` (extended): asserts `{ clientSecret }` response shape with the correct `subscriptions.create` call args (mocked Stripe SDK), and asserts no `UPDATE users SET tier` query fires — per Inputs/Outputs above.
  - `npm run build`, `npm run type-check`, `npm run lint` all PASS — including confirming `@stripe/stripe-js`/`@stripe/react-stripe-js` are used only in Client Components (`web/app/account/upgrade/page.tsx`, `web/lib/stripeClient.ts`) and never pulled into server-only bundles (checked via Next.js's build output route-size table).
  - **Explicitly deferred**: live end-to-end verification (real embedded Payment Element → real Stripe test-mode card → real confirmation) is deferred until the human supplies real Stripe test-mode credentials locally, per the human's explicit instruction — noted here, not silently skipped, matching spec 016's own precedent for the identical situation.
- **Intellectual Control**: The `/upgrade` route rewrite is the piece of this spec most at risk of accidentally regressing spec 016's central invariant (the route's own response must never write `tier`), precisely because it's rewriting that route's success-path body — the explicit "no `UPDATE users SET tier` fires" test assertion makes that invariant provable after this specific edit, not just assumed to have survived.
- **Constraints**: `/api/users/upgrade`'s response must never itself set `tier = 'premium'` under any code path — unchanged from spec 016, re-tested here per the Verification Oracle. `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (already in `.env.example` per spec 016, previously unused) becomes actually consumed by `web/lib/stripeClient.ts` — no new env var needed. This spec does not edit `web/app/api/webhooks/stripe/route.ts` — the webhook still listens for spec 016's original events only, meaning `users.tier` will NOT actually flip to `'premium'` after a real payment confirms until spec 023 adds the correct event case; this spec's own Verification Oracle does not depend on that (it tests the `/upgrade` route and payment UI in isolation, with mocked Stripe), but this gap is called out explicitly here so it isn't mistaken for complete, working payment infrastructure on its own — spec 023 is required before this feature works end-to-end in production.
- **Edge Cases**: `stripe.confirmPayment()` fails (declined card, etc.) → inline error on `/account/upgrade`, no redirect, user can retry without a fresh `POST /api/users/upgrade` call reusing the same `clientSecret` (Stripe's own Payment Element supports retry against the same PaymentIntent). A signed-out user hits `/account/upgrade` directly (no session cookie) → `POST /api/users/upgrade` returns its existing `401`, page shows a "sign in first" message with a link to `/login`, not a crash. Payment confirmed client-side but the webhook hasn't landed yet when `/account/upgrade` redirects to `callbackUrl` (webhook delivery is asynchronous, same as spec 016's original design) → the destination page may still show a paywall for a few seconds until the webhook updates `tier` (once spec 023 lands); this spec does not attempt to solve webhook-delivery latency with client-side polling, but the page's own "processing" state makes the wait visible rather than looking broken.

Any implementation choice that would make `/upgrade`'s own response start writing `tier` is a hard violation, tested explicitly.
2. Simplicity > Pattern purity   (always present unless explicitly overridden)

OVERRIDE (project decision, 2026-08-05): Pattern purity > Simplicity for this project — applied by keeping the client-side Stripe singleton (`getStripeJsPromise()`) in the same `getXxx()` naming/lazy-init shape as every other singleton in this codebase, rather than a bespoke pattern just for this one client SDK.
4. **Explicit, human-directed reversal of spec 016 Force #3 > silent architectural drift** — per this spec's own "Scoped reversal" note above: switching from Checkout-redirect to embedded Payment Element is a real, deliberate change to a previously-justified decision, made on explicit 2026-08-16 human instruction, and is documented as a reversal (with the PCI-scope property re-verified as preserved) rather than presented as if spec 016 never made a considered choice here.
5. **Route-rewrite split from webhook-correction > bundling both in one spec** — per the Split note above: this spec's own file list already reaches cap without the webhook edit; keeping the webhook fix in spec 023 (where it belongs alongside the signup hand-off, since both are about "what happens after the payment UI this spec builds") keeps both specs genuinely reviewable.
