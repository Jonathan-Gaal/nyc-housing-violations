[SPEC]
- **Objective**: Two remaining pieces to make in-app premium payment actually work end to end: (a) correct `web/app/api/webhooks/stripe/route.ts` to listen for the events Stripe genuinely fires for a `payment_behavior: 'default_incomplete'` subscription (spec 022's flow) instead of the Checkout-only event spec 016 originally listened for; (b) confirm spec 018's `/signup?intent=premium` hand-off actually completes the payment step, by redirecting to spec 022's `/account/upgrade` page (which performs `POST /api/users/upgrade` and renders the Payment Element there) rather than rendering payment UI inline on the signup page itself. **Depends on spec 022** (`/api/users/upgrade`'s `{ clientSecret }` response and the `/account/upgrade` page this spec redirects to) **and spec 018** (`/signup`'s existing `intent=premium` → `/account/upgrade` redirect contract, which this spec confirms/completes) — both referenced, not duplicated.
- **Human-approved scope note**: proceeds under the 2026-08-12 override (specs 014-016) plus the 2026-08-16 human decision authorizing in-app payment and this specific hand-off.
- **Split note (2026-08-16, per coordinator correction)**: this spec did not exist in the original three-spec plan (018/019/020) — it is new, created specifically to keep spec 022 (payment route + page) at or under the hard 5-file GRANULARITY cap without leaving the webhook-event fix or the signup-page wiring undone. See spec 022's own Split note for the full chain of reasoning.
- **Settled decision (2026-08-16, human decision via coordinator, resolving optimus-prime's flagged open item)**: the redirect-to-`/account/upgrade` approach (previously "option (i)") is the chosen and only path — not a builder's call. The signup page never renders the Payment Element inline and never calls `POST /api/users/upgrade` itself; it performs exactly one job for the `intent=premium` case, which is redirecting to `/account/upgrade?callbackUrl=<original callbackUrl>` per spec 018's existing contract. All payment-step work (calling `/api/users/upgrade`, rendering `Elements`/`PaymentElement`, calling `stripe.confirmPayment()`) happens exclusively on spec 022's `/account/upgrade` page, which was already built to do this. This spec's remaining job on the signup side is verification only — confirming spec 018's redirect already satisfies the full `intent=premium` flow with no further edit needed to `signup/page.tsx` — plus the webhook correction, which is unrelated to this choice and unchanged by it.
- **Webhook event correction — settled, not an open question for the builder** (per 2026-08-16 coordinator correction, verified against Stripe's own Elements + PaymentIntents API subscription integration guide, not the Checkout guide spec 016 originally followed): `checkout.session.completed` **never fires** for this flow — that event is Checkout-only and is never emitted for a subscription created directly via `stripeClient.subscriptions.create(...)` (spec 022's approach). The correct, confirmed events are `customer.subscription.created` and `customer.subscription.updated` — on either, check `event.data.object.status === 'active'` before granting premium (a `default_incomplete` subscription's `status` starts as `'incomplete'` and transitions to `'active'` once the initial payment confirms; both `.created` and `.updated` can carry a non-`'active'` status depending on timing, so the status check, not just the event type, is what actually gates the grant). `customer.subscription.deleted` handling (spec 016's existing `handleSubscriptionDeleted`) is unchanged — still the revocation path.
- **Inputs/Outputs**:
  - Output (edit): `web/app/api/webhooks/stripe/route.ts` — replace the `checkout.session.completed` case (spec 016's `handleCheckoutSessionCompleted`, which is now dead code for this flow — see Constraints for why it is removed rather than left in place) with two new cases, `customer.subscription.created` and `customer.subscription.updated`, both routed to a new `handleSubscriptionActivated(subscription: Stripe.Subscription)` function: extracts `firebase_uid` via the existing `extractFirebaseUid()` helper (subscription-level `metadata`, already set by spec 022's `subscriptions.create({ ..., metadata: { firebase_uid } })` call), and if `subscription.status === 'active'`, calls the existing `setUserTier(firebaseUid, 'premium', stripeCustomerId, null)` — if `status` is anything else (e.g. `'incomplete'`), the handler returns without writing `tier` (not every `.created`/`.updated` event means "grant premium," only the one(s) where status has actually reached `'active'`). Reuses `setUserTier()`'s existing idempotency (`UPDATE ... WHERE firebase_uid = $1`, safe to run repeatedly) — required here specifically because `.updated` fires on every subsequent lifecycle change too (renewals, plan changes), not just the initial activation, so the handler must not assume "this is the first payment" and must tolerate being called many times over a subscription's life with the same eventual no-op result once `tier` is already `'premium'`.
  - Output (edit): `web/app/api/webhooks/stripe/route.test.ts` (spec 016's existing test file) — extended: (a) `customer.subscription.created` with `status: 'active'` and a resolvable `firebase_uid` → `tier` updated to `'premium'`; (b) `customer.subscription.created` with `status: 'incomplete'` → `tier` NOT updated (proving the status check actually gates the grant, not just the event type); (c) `customer.subscription.updated` fired a second time with `status: 'active'` (simulating a renewal) after `tier` is already `'premium'` → no error, idempotent no-op; (d) `customer.subscription.deleted` still reverts `tier` to `'free'`, unchanged from spec 016; (e) existing signature-verification-mandatory tests (valid signature required, invalid/missing → `400`, no DB write) continue to pass unmodified.
  - Output (verification, not necessarily a code edit): `web/app/(auth)/signup/page.tsx` (spec 018's file) — confirms the `intent=premium` hand-off contract spec 018 defined is complete as-is: on successful account creation + session exchange, when `intent === 'premium'`, the page redirects to `/account/upgrade?callbackUrl=<callbackUrl, or '/' if absent>` (spec 022's page) and does nothing further — no `POST /api/users/upgrade` call and no `Elements`/`PaymentElement` rendering on `signup/page.tsx` itself, ever. Spec 022's `/account/upgrade` page (already built, reads its own `callbackUrl` param, performs `POST /api/users/upgrade`, renders the Payment Element, and on confirmed payment success redirects to that `callbackUrl`) is the entire payment step. If review of spec 018's shipped implementation finds the redirect doesn't already carry `callbackUrl` through correctly, this spec's job includes the small fix to make it do so exactly — but the destination and mechanism (redirect, not inline render) are fixed, not open.
- **Design Pattern**: Webhook status-check-not-just-event-type is the core correction here — Stripe's event *type* (`customer.subscription.created`/`.updated`) is necessary but not sufficient to know payment succeeded; the subscription's `status` field is the actual signal, checked explicitly rather than inferred from which event fired. Separately, the signup→upgrade hand-off follows this codebase's existing `callbackUrl`-query-param redirect pattern (same shape as `middleware.ts`'s redirect-to-`/login?callbackUrl=...` and spec 018's own `/signup?callbackUrl=...`) rather than inventing a same-page inline flow — one dedicated page per step (account creation, then payment), consistent with spec 018's own Force #3 (a teachable auth/payment flow has one page per user intent, not one page overloaded with both).
- **Bounded-AI boundary**: 100% deterministic. Event-type/status branching is a plain conditional on Stripe's own webhook payload; `tier` writes remain exclusively through `setUserTier()`, unchanged from spec 016. The signup→upgrade hand-off is a plain conditional redirect on a query-string value. No LLM involvement.
- **Verification Oracle**: `web/app/api/webhooks/stripe/route.test.ts` covers all five assertions in Inputs/Outputs above (mocked Stripe SDK/webhook signing, matching spec 016's existing test approach — no live `whsec_`/`sk_test_` credentials required). `web/e2e/features/auth.spec.ts` (spec 018's file, extended) or a new signup-payment e2e test asserts: completing `/signup?intent=premium&callbackUrl=%2Flandlord` redirects the browser to `/account/upgrade?callbackUrl=%2Flandlord` — a real navigation, not an inline render on `/signup` — and that no `POST /api/users/upgrade` request is ever fired from `signup/page.tsx` itself (network-request spy scoped to that page only; the request firing from `/account/upgrade` after navigation is expected and out of this assertion's scope, covered instead by spec 022's own tests). `npm run build`, `npm run type-check`, `npm run lint` all PASS.
- **Intellectual Control**: The original spec (before this correction) flagged the webhook event name as an open question for the builder to verify against Stripe's docs — that ambiguity is exactly the kind of gap that produces a payment that succeeds in Stripe's dashboard while `users.tier` silently never updates, a failure mode invisible in casual manual testing (Stripe confirms payment; only this app's own DB is wrong). Resolving it here as a settled fact, with an explicit test asserting the `status === 'incomplete'` case does NOT grant premium, closes that gap provably rather than leaving it as documentation the builder might skip verifying. Separately, fixing the signup→upgrade hand-off as redirect-only (not inline-or-redirect) removes a second ambiguity optimus-prime flagged before it could cause a builder to duplicate payment-rendering logic across two pages (signup and upgrade), which would have created two divergent code paths handling the same Stripe PaymentIntent confirmation — a real drift risk the settled decision avoids by keeping payment UI in exactly one place.
- **Constraints**: `handleCheckoutSessionCompleted()` (spec 016's original handler) is removed from the switch statement, not left dead-but-reachable — since spec 022 never creates a Checkout Session, `checkout.session.completed` will never fire in this app's actual usage going forward, and leaving an unreachable case in the switch would misleadingly suggest Checkout is still a live path. `customer.subscription.deleted` handling and `setUserTier()`/`extractFirebaseUid()` helpers are reused unchanged, not reimplemented. This spec does not alter the `default_incomplete`/`expand` mechanics from spec 022's `/upgrade` route — it only consumes the resulting subscription metadata via the webhook. `web/app/(auth)/signup/page.tsx` must never import `@stripe/stripe-js`/`@stripe/react-stripe-js` or call `POST /api/users/upgrade` — per the Settled decision above, that is exclusively `/account/upgrade`'s responsibility; a future editor adding Stripe imports to the signup page would be reintroducing the rejected inline-rendering option.
- **Edge Cases**: A `customer.subscription.updated` event with no resolvable `firebase_uid` in metadata (shouldn't happen given spec 022 always sets it, but defensively, e.g. a subscription created outside this app's own flow) → logged as an anomaly per the existing `extractFirebaseUid()` null-handling pattern, no speculative write. A `customer.subscription.updated` event where `status` transitions from `'active'` back to `'past_due'` (a failed renewal charge) → this spec's `handleSubscriptionActivated` only acts on `status === 'active'`; a non-active status on `.updated` is a no-op here (not a revocation) since `customer.subscription.deleted` remains the only revocation trigger, matching spec 016's original design — a `past_due` subscription is not explicitly handled by this spec and is noted as a known gap, not silently assumed to keep `tier` accurate in that specific case (flagged for a future spec, not fabricated as in-scope here). Signup with `intent=premium` where the user closes the tab before completing payment → the account was already created (Firebase account creation happens before the redirect to `/account/upgrade`) with `tier` remaining `'free'` — the user can sign back in and reach `/account/upgrade` later; no orphaned or half-created state. User lands on `/account/upgrade` via the signup redirect but then navigates away before confirming payment → same as above, `tier` stays `'free'`, no special handling needed beyond what spec 022 already defines for a signed-out or payment-not-yet-confirmed visit to that page.
